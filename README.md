# taskflow-multi-db

[![CI](https://github.com/mbeltran93/taskflow-multi-db/actions/workflows/ci.yml/badge.svg)](https://github.com/mbeltran93/taskflow-multi-db/actions/workflows/ci.yml)

Una **misma aplicacion Spring Boot** (mismo JAR, mismas entidades JPA, mismo codigo Java)
que corre indistintamente contra **PostgreSQL, MySQL, SQL Server u Oracle**, cambiando
unicamente el perfil de Spring activo. No son 4 apps separadas: es una sola capa de
dominio y persistencia que demuestra que, si el acceso a datos esta bien disenado
(JPA/Hibernate + migraciones versionadas por vendor), el motor de base de datos se
convierte en un detalle de configuracion, no en una decision que contamina el codigo.

Repo hermano dentro del mismo portafolio de `mbeltran93`, modelando el mismo dominio
reducido tipo Trello/Jira (`User`, `Project`, `Task`) que otros proyectos de la serie
(por ejemplo `taskflow-spring-boot`), pero con el foco puesto exclusivamente en la
**portabilidad de la capa de datos**.

## Por que importa esto

En un trabajo real casi nunca elegis la base de datos desde cero: te la imponen (un
cliente ya tiene Oracle, otro exige SQL Server porque es shop de Microsoft, otro usa
Postgres/MySQL porque es lo gratuito). Saber que tu capa de persistencia **no esta
casada con un vendor** es una habilidad concreta. Este repo la demuestra en la practica,
no en la teoria:

- Las **entidades JPA son literalmente las mismas** (`User`, `Project`, `Task`, un solo
  `@Id @GeneratedValue(strategy = GenerationType.IDENTITY)` en los tres) para los 4
  motores. Hibernate traduce eso a `BIGSERIAL` en Postgres, `AUTO_INCREMENT` en MySQL,
  `IDENTITY(1,1)` en SQL Server y una columna `IDENTITY` nativa en Oracle 23c.
- El **esquema SQL real no es igual** entre vendors y este repo no lo esconde: cada uno
  tiene su propio changelog de Liquibase en `src/main/resources/db/changelog/<vendor>/`.
  Ahi se ve, lado a lado, cada diferencia real que encontre al portar el esquema:

  | Concepto | PostgreSQL | MySQL | SQL Server | Oracle |
  |---|---|---|---|---|
  | Autoincremento | `BIGSERIAL` | `BIGINT AUTO_INCREMENT` | `BIGINT IDENTITY(1,1)` | `NUMBER GENERATED BY DEFAULT AS IDENTITY` |
  | Texto variable | `VARCHAR(n)` | `VARCHAR(n)` | `NVARCHAR(n)` (Unicode) | `VARCHAR2(n)` |
  | Timestamp por defecto | `TIMESTAMP DEFAULT now()` | `DATETIME DEFAULT CURRENT_TIMESTAMP` | `DATETIMEOFFSET(6) DEFAULT SYSDATETIMEOFFSET()` | `TIMESTAMP WITH TIME ZONE DEFAULT SYSTIMESTAMP` |
  | Motor/engine explicito | no aplica | `ENGINE=InnoDB` (si no, MyISAM sin FKs) | no aplica | no aplica |
  | Base de datos por defecto | la que declares | la que declares | solo crea `master`, hay que crear la propia a mano (ver mas abajo) | pluggable DB `FREEPDB1`, crea el usuario solo con `APP_USER`/`APP_USER_PASSWORD` |
  | Booleans / enums | nativo `VARCHAR` + check opcional | igual | igual | igual (Oracle no tiene `BOOLEAN` utilizable asi en tablas hasta 23c, se evito para no atarse a la version) |

- **El `created_at` (`java.time.Instant` en las 3 entidades) necesita una columna
  "con zona horaria" en SQL Server y Oracle, pero no en Postgres/MySQL.** Hibernate 6
  mapea `Instant` al tipo JDBC `TIMESTAMP_UTC`. En Postgres y MySQL, una columna
  `TIMESTAMP`/`DATETIME` lisa es suficiente (ambos la validan y la extraen bien). En SQL
  Server, Hibernate **exige** `datetimeoffset` para ese tipo: con `datetime2` la app ni
  arranca (falla la validacion de esquema al boot). En Oracle, una columna `TIMESTAMP`
  lisa pasa la validacion de esquema, pero el driver `ojdbc11` tira
  `ORA-18716: {0} not in any time zone` en runtime al intentar extraerla como `Instant`;
  hace falta `TIMESTAMP WITH TIME ZONE`. Los dos bugs (y el fix, en el changelog de cada
  vendor) estan detallados en la seccion "Que se probo realmente" mas abajo.

- **Herramienta de migraciones: Liquibase, no Flyway.** Lo probe primero con Flyway,
  pero Flyway movio el soporte de Oracle (y de varios otros vendors "enterprise") a su
  edicion de pago (Teams/Redgate) hace ya varias versiones; el modulo community
  (`flyway-core`) ya no trae Oracle. Liquibase sí soporta Oracle en su edicion
  100% open source (`liquibase-core`), asi que es la opcion que realmente cumple el
  objetivo de "correr contra los 4 motores sin pagar licencia". Esta decision, y el
  porque, es en si misma parte de lo que este repo quiere mostrar.
- `spring.jpa.hibernate.ddl-auto=validate` en los 4 perfiles: Hibernate **nunca** crea
  ni modifica tablas, solo valida que las entidades coincidan con lo que dejaron las
  migraciones de Liquibase. El esquema versionado es la unica fuente de verdad.

## Stack

- Java 17, Spring Boot 3.3.4 (Web, Data JPA, Validation)
- Liquibase (migraciones versionadas, una carpeta de changelog por vendor)
- Drivers oficiales: `postgresql`, `mysql-connector-j`, `mssql-jdbc`, `ojdbc11` (el
  driver thin de Oracle esta publicado gratis en Maven Central, sin licencia)
- Lombok, Spring Security Crypto (solo `BCryptPasswordEncoder`, sin traer toda la
  config de Spring Security: el foco de este repo es la capa de datos, no auth)
- Testcontainers + JUnit 5 para los tests de integracion
- Docker Compose con los 4 motores

## El dominio (identico en los 4 motores)

- **User**: `id, name, email (unico), passwordHash, createdAt`
- **Project**: `id, name, description, ownerId (FK a User), createdAt`
- **Task**: `id, title, description, status (TODO | IN_PROGRESS | DONE), projectId (FK a Project), assigneeId (FK a User, nullable), dueDate (nullable), createdAt`

## Endpoints REST

CRUD estandar para los tres recursos (sin JWT: el alcance de este repo es la
portabilidad de persistencia, no autenticacion):

```
POST   /api/users            GET /api/users       GET /api/users/{id}
PUT    /api/users/{id}       DELETE /api/users/{id}

POST   /api/projects         GET /api/projects    GET /api/projects/{id}
PUT    /api/projects/{id}    DELETE /api/projects/{id}
GET    /api/projects/{id}/tasks               GET /api/projects/{id}/tasks?status=TODO
POST   /api/projects/{id}/close

POST   /api/tasks            GET /api/tasks       GET /api/tasks/{id}
PUT    /api/tasks/{id}       DELETE /api/tasks/{id}
```

Respuestas de error uniformes (`ApiError`: timestamp, status, error, message, details)
para 400 (validacion), 404 (no encontrado) y 409 (violacion de integridad, por ejemplo
un `projectId` o `assigneeId` que no existe).

### `GET /api/projects/{id}/tasks?status=`

El filtro por status es opcional (`?status=TODO|IN_PROGRESS|DONE`); sin el query param
se comporta como antes (todas las tareas del proyecto). Con el filtro, pasa a ejecutar
`WHERE project_id = ? AND status = ?`, la query que motiva el indice compuesto de la
seccion "Tuning de performance" mas abajo.

### `POST /api/projects/{id}/close`

Cierra un proyecto: marca como `DONE` todas sus tareas que no lo estaban y devuelve
cuantas se actualizaron (`{"projectId": 1, "updatedTasks": 4}`). 404 si el proyecto no
existe.

```bash
curl -X POST http://localhost:8080/api/projects/1/close
```

El mecanismo real detras de este endpoint **no es el mismo en los 4 motores**, a
proposito, para mostrar stored procedures reales donde el dominio los pide (Oracle y
SQL Server) sin forzarlos donde no eran parte del alcance:

- **Oracle**: llama al stored procedure PL/SQL `close_project(p_project_id, p_updated_count)`
  (`db/changelog/oracle/changelog-master.yaml`, changeset `2-close-project-procedure`).
  El UPDATE corre del lado de la base, y la cantidad de filas afectadas vuelve en un
  parametro `OUT NUMBER` via `SQL%ROWCOUNT`. `OracleProjectCloser` (en
  `service/OracleProjectCloser.java`) lo invoca con `SimpleJdbcCall`, declarando los
  parametros a mano (`withoutProcedureColumnMetaDataAccess()`) para no depender de que
  el driver pueda introspeccionar la metadata del procedure.
- **SQL Server**: mismo contrato, stored procedure T-SQL `close_project` con
  `@ProjectId BIGINT` de entrada y `@UpdatedCount INT OUTPUT`, usando `@@ROWCOUNT`
  (`db/changelog/sqlserver/changelog-master.yaml`, changeset
  `2-close-project-procedure`). `SqlServerProjectCloser` lo invoca tambien con
  `SimpleJdbcCall`.
- **Postgres y MySQL**: no se agrego una stored procedure propia para estos 2 motores
  (no era parte del alcance pedido); `JpqlProjectCloser` hace el mismo UPDATE masivo
  pero via JPQL/Hibernate (`TaskRepository.closeAllTasksOfProject`). El resultado
  observable desde la API es identico en los 4 motores.

La seleccion de implementacion es por perfil de Spring (`@Profile("oracle")`,
`@Profile("sqlserver")`, `@Profile({"postgres", "mysql"})` sobre 3 beans que
implementan la misma interfaz `ProjectCloser`), inyectada en `ProjectService.close()`.
Ningun controller ni servicio tiene un `if (vendor == ...)`: el vendor activo decide,
via Spring, que bean se inyecta.

**Probado de punta a punta contra los 2 motores con stored procedure real** (ademas de
Postgres/MySQL con el fallback JPQL, los 4 verificados por HTTP real con `curl`):

- Oracle (`docker compose up -d oracle`, perfil `oracle`): se creo un proyecto con 4
  tareas en `TODO`, se llamo `POST /api/projects/{id}/close` y devolvio
  `{"updatedTasks": 4}`; un `GET` posterior confirmo las 4 tareas en `DONE`.
- SQL Server (`docker compose up -d sqlserver`, perfil `sqlserver`): mismo flujo con 3
  tareas, devolvio `{"updatedTasks": 3}`, confirmado con un `GET` posterior.

## Como correrlo contra cada motor

Requisitos: JDK 17+, Maven (o el wrapper si lo generas: `mvn -N wrapper:wrapper`),
Docker Desktop con Docker Compose v2.

Los 4 servicios de base de datos viven en el mismo `docker-compose.yml`, pero la app
solo se conecta a **uno a la vez** segun el perfil activo. Levanta nada mas el que vas
a usar (`docker compose up -d <servicio>` arranca solo ese servicio, no los 4).

### PostgreSQL

```bash
docker compose up -d postgres
mvn spring-boot:run -Dspring-boot.run.profiles=postgres
```

### MySQL

```bash
docker compose up -d mysql
mvn spring-boot:run -Dspring-boot.run.profiles=mysql
```

### SQL Server

SQL Server no crea una base de datos propia al arrancar (solo `master`), asi que hay
que crear `taskflow` una vez, a mano, la primera vez:

```bash
docker compose up -d sqlserver
# esperar ~15-20s a que el motor termine de arrancar, despues:
docker exec -it taskflow-sqlserver /opt/mssql-tools18/bin/sqlcmd \
  -S localhost -U sa -P 'TaskflowStrong!Passw0rd' -C \
  -Q "CREATE DATABASE taskflow"

mvn spring-boot:run -Dspring-boot.run.profiles=sqlserver
```

### Oracle

`gvenzl/oracle-free` crea el usuario/schema `taskflow` automaticamente en la pluggable
database `FREEPDB1` la primera vez que arranca (variables `APP_USER` /
`APP_USER_PASSWORD` en el `docker-compose.yml`), sin pasos manuales. Ese primer arranque
puede tardar **varios minutos** mientras inicializa los datafiles (podes seguirlo con
`docker compose logs -f oracle`, avisa "DATABASE IS READY TO USE!" cuando termina):

```bash
docker compose up -d oracle
# esperar a que el log diga "DATABASE IS READY TO USE!"
mvn spring-boot:run -Dspring-boot.run.profiles=oracle
```

### Apagar todo

```bash
docker compose down          # para los contenedores, conserva los volumenes/datos
docker compose down -v       # ademas borra los datos (arranque limpio la proxima vez)
```

## Tests

### Unitarios / rapidos

```bash
mvn test
```

(Hoy no hay tests puramente unitarios ademas de los de integracion; este comando queda
documentado para cuando se agreguen tests de servicios con mocks.)

### Integracion con Testcontainers

```bash
mvn verify
```

Los tests de integracion siguen la convencion `*IT.java` y corren con el plugin
`maven-failsafe-plugin` en la fase `verify` (separados de los unitarios, que corren
mas rapido con `mvn test`). La logica de los tests vive una sola vez en
`AbstractCrudIT` (crear usuario -> crear proyecto -> crear tarea -> listar -> actualizar
-> borrar -> 404 -> 400 de validacion) y cada subclase la corre contra un contenedor
real distinto, levantado y destruido automaticamente por Testcontainers:

- `PostgresCrudIT` y `MySqlCrudIT`: **habilitados por defecto** en el codigo (sin
  `@Disabled`), pensados para correr en cualquier `mvn verify` con imagenes livianas
  (`postgres:16-alpine`, `mysql:8.4`). Ver la nota de abajo: en esta maquina puntual
  hoy tampoco logran arrancar, por el mismo motivo que `SqlServerCrudIT`/`OracleCrudIT`.
- `SqlServerCrudIT` y `OracleCrudIT`: **mismo codigo de test, misma clase base**, pero
  siguen con `@Disabled` puesto a proposito. Ya **no** es por el peso/tiempo de descarga
  de las imagenes (eso se resolvio liberando espacio en disco, ver seccion de abajo): es
  por el mismo problema de Testcontainers-vs-Docker-Desktop descrito abajo. El CRUD
  completo contra SQL Server y Oracle reales **si esta verificado**, solo que por fuera
  de Testcontainers (`docker compose` + `curl`, ver seccion siguiente). Para intentar
  habilitarlas en una maquina sin ese problema: sacar el `@Disabled` de la clase y
  correr `mvn verify -Dit.test=SqlServerCrudIT` o `-Dit.test=OracleCrudIT` con Docker
  disponible y tiempo de sobra.

> **Nota sobre esta maquina en particular (actualizado 2026-10-01):** en la Windows +
> Docker Desktop donde se construyo y se re-verifico este repo, Testcontainers no logra
> hablar con el daemon: el named pipe que expone Docker Desktop le devuelve a clientes
> que no son el CLI oficial (`docker.exe`) una respuesta "stub" (un `docker info` vacio
> con el label `com.docker.desktop.address=npipe://./pipe/docker_cli`), algo conocido en
> versiones recientes de Docker Desktop para Windows cuando un cliente de terceros
> (docker-java, la libreria que usa Testcontainers) intenta hablarle directo al engine
> por fuera del CLI. Esto se documento originalmente solo para `SqlServerCrudIT`/
> `OracleCrudIT` (nunca se habian llegado a correr), pero al retomar el proyecto el
> 2026-10-01 (disco liberado, Docker Desktop recien reiniciado) se confirmo que el
> problema es **mas amplio de lo que decia esta nota antes**: tambien bloquea a
> `PostgresCrudIT` y `MySqlCrudIT`, que son las que este README llegó a describir como
> "habilitadas por defecto, corren en cualquier `mvn verify`" — hoy, en esta maquina, un
> `mvn verify` limpio **falla** en la fase de integration-test por esto, para los 4
> vendors por igual, con o sin `@Disabled`. Se probo tambien forzar
> `DOCKER_HOST=npipe:////./pipe/dockerDesktopLinuxEngine` para apuntar directo al pipe
> del engine en vez del proxy del CLI: mismo error. El `docker` CLI y `docker compose`
> andan perfectos en la misma maquina (por eso toda la verificacion real de los 4
> motores, incluida la nueva de SQL Server y Oracle, se hizo con `docker compose` +
> `curl`, no con Testcontainers). Si te pasa lo mismo: probalo en Linux/Mac, en CI, o
> con Docker Desktop usando WSL2 con el socket expuesto directo a la distro — ahi
> Testcontainers funciona sin este problema. El codigo de los tests en si no cambia.

## Que se probo realmente y que quedo solo documentado

Honestidad ante todo: esto se construyo y se verifico en una maquina con Docker
Desktop para Windows. Actualizado el 2026-10-01: **los 4 motores estan verificados de
punta a punta por HTTP real**, algo que no era cierto para SQL Server y Oracle en la
version anterior de este README (se habian quedado solo documentados porque el disco
C: se quedo sin espacio durante el desarrollo). Al liberar espacio se pudo terminar de
levantar los 4 contenedores y correr el flujo completo contra cada uno.

- **PostgreSQL**: probado de punta a punta. `docker compose up -d postgres`, la app
  arranca con el perfil `postgres`, Liquibase corre `db/changelog/postgres/` contra una
  base vacia, Hibernate valida el esquema, y el flujo completo (crear usuario -> crear
  proyecto -> crear tarea -> listarla por proyecto -> actualizar su estado -> borrarla
  -> 404 tras el borrado) se probo por HTTP real con `curl`.
- **MySQL**: mismo procedimiento, mismo flujo completo probado por HTTP contra
  `docker compose up -d mysql` con el perfil `mysql`, incluyendo el chequeo de `400`
  por email duplicado.
- **SQL Server**: probado de punta a punta. `docker compose up -d sqlserver`, se creo
  la base `taskflow` a mano (ver seccion de arriba), la app arranco con el perfil
  `sqlserver`, Liquibase corrio `db/changelog/sqlserver/` y el flujo HTTP completo
  (crear usuario -> proyecto -> tarea -> listar -> actualizar estado -> borrar -> 404)
  se probo con `curl`. En el camino aparecio un bug real, ya corregido: Hibernate 6
  mapea `java.time.Instant` (el tipo de los 3 `createdAt`) al tipo JDBC `TIMESTAMP_UTC`,
  y para `SQLServerDialect` eso exige una columna `datetimeoffset`, no `datetime2` (el
  changelog original usaba `DATETIME2 DEFAULT SYSUTCDATETIME()`). Sin el fix, la app ni
  arrancaba: fallaba la validacion de esquema de Hibernate al boot
  (`SchemaManagementException: wrong column type encountered in column [created_at]...
  found [datetime2], but expecting [datetimeoffset(6)]`). Se corrigio el changelog de
  SQL Server a `DATETIMEOFFSET(6) DEFAULT SYSDATETIMEOFFSET()` en las 3 tablas.
- **Oracle**: probado de punta a punta. `docker compose up -d oracle`, se espero el
  log `DATABASE IS READY TO USE!` (unos 2-3 minutos en el primer arranque), la app
  arranco con el perfil `oracle` y el mismo flujo HTTP completo se probo con `curl`.
  Tambien aparecio un bug real, distinto al de SQL Server pero de la misma familia:
  Hibernate si dejo pasar la validacion de esquema contra una columna `TIMESTAMP` lisa,
  pero al extraer esa columna como `Instant` el driver `ojdbc11` tiraba en runtime
  `ORA-18716: {0} not in any time zone.DATE` en cualquier `GET` que tocara una fila
  existente (se veia en la creacion, que hace INSERT + devuelve el objeto ya en
  memoria, pero reventaba apenas se hacia un SELECT real: listar tareas de un proyecto,
  actualizar o borrar una tarea). El fix fue el mismo patron que en SQL Server: la
  columna `created_at` tiene que ser `TIMESTAMP WITH TIME ZONE` (no `TIMESTAMP` a
  secas) para que el driver pueda reconstruir el `Instant` sin ambiguedad de zona
  horaria. Se corrigio el changelog de Oracle en las 3 tablas, manteniendo
  `DEFAULT SYSTIMESTAMP` (que ya devuelve tipo "with time zone" en Oracle).

### Tests de integracion con Testcontainers: estado real

Mas alla del flujo HTTP (que si quedo verificado para los 4 motores), los tests
`*CrudIT` que usan Testcontainers **no se pudieron ejecutar para ninguno de los 4
vendors en esta maquina**, por el problema de Docker Desktop para Windows + docker-java
descrito en la seccion de Tests mas arriba (el named pipe le devuelve a Testcontainers
un `docker info` "stub"). Esto afecta por igual a `PostgresCrudIT`/`MySqlCrudIT` (que
en versiones anteriores de este README se describian como ya verificadas via
Testcontainers) y a `SqlServerCrudIT`/`OracleCrudIT` (que se dejan con `@Disabled`).
No es un problema de los tests ni del codigo de produccion: el mismo CRUD que esos
tests ejercitan via MockMvc esta probado y funcionando por HTTP real con `curl` contra
los 4 motores, segun el detalle de arriba.

Si alguien clona este repo en una maquina sin este problema de Docker Desktop (Linux,
Mac, CI, o Windows con WSL2 y el socket expuesto directo a la distro), no falta nada de
configuracion: sacar el `@Disabled` de `SqlServerCrudIT`/`OracleCrudIT` y correr
`mvn verify` (o `mvn verify -Dit.test=NombreDeLaClase` para una sola) deberia correr
las 4 suites sin cambios de codigo.

## Tuning de performance

El endpoint `GET /api/projects/{id}/tasks?status=` (y `TaskRepository.findByProjectIdAndStatus`)
hace `WHERE project_id = ? AND status = ?`. Hasta esta seccion, el unico indice relevante
era `idx_tasks_project_id` (una sola columna, creado en el changeset `1-create-schema`
original de cada vendor), asi que el motor podia usar ese indice para acotar por
`project_id` pero tenia que revisar cada fila candidata para aplicar el filtro de
`status` aparte. Se agrego un indice compuesto `idx_tasks_project_status ON
tasks(project_id, status)` via un changeset nuevo de Liquibase en los 4 vendors
(`2-idx-tasks-project-status` en Postgres/MySQL, `3-idx-tasks-project-status` en
Oracle/SQL Server, despues del changeset del stored procedure).

Esto se midio de verdad, no es un ejemplo inventado: se levantaron los contenedores
reales de Postgres y MySQL (`docker compose up -d postgres mysql`), se sembraron **49
proyectos y 300.000 tareas** distribuidas al azar entre ellos (asi `project_id` es
selectivo: ~6000 filas de 300.000 por proyecto, y el filtro de `status` parte eso en
~3), se corrio el plan de ejecucion contra el proyecto `id=1` **antes** de crear el
indice compuesto, se agrego el indice (el mismo changeset de Liquibase, aplicado con la
app corriendo), y se volvio a correr el mismo plan **despues**. Se eligieron estos 2
motores por ser los mas rapidos de levantar con datos reales de prueba; SQL Server y
Oracle ya tenian su propia verificacion (la de los stored procedures, arriba) y
agregarles tambien el seed de 300k filas no sumaba nada nuevo a lo que ya mostraban
Postgres/MySQL sobre el mismo indice.

### PostgreSQL

Query: `SELECT * FROM tasks WHERE project_id = 1 AND status = 'TODO';`

**Antes** (solo `idx_tasks_project_id`) — `EXPLAIN (ANALYZE, BUFFERS)`:

```
Bitmap Heap Scan on tasks  (cost=82.86..5274.79 rows=2032 width=102) (actual time=1.038..9.066 rows=1999 loops=1)
  Recheck Cond: (project_id = 1)
  Filter: ((status)::text = 'TODO'::text)
  Rows Removed by Filter: 3966
  Heap Blocks: exact=3439
  Buffers: shared hit=3448
  ->  Bitmap Index Scan on idx_tasks_project_id  (cost=0.00..82.35 rows=6140 width=0) (actual time=0.728..0.729 rows=5965 loops=1)
        Index Cond: (project_id = 1)
        Buffers: shared hit=9
Planning Time: 1.103 ms
Execution Time: 9.240 ms
```

El indice de una sola columna trae las ~5965 filas del proyecto y recien ahi un
`Filter` descarta 3966 (las que no son `TODO`) leyendo la fila entera para cada una.

**Despues** (con `idx_tasks_project_status`) — mismo query, cache ya tibia en ambas
corridas para que la comparacion sea justa:

```
Bitmap Heap Scan on tasks  (cost=29.24..3809.61 rows=2031 width=102) (actual time=0.646..3.797 rows=1999 loops=1)
  Recheck Cond: ((project_id = 1) AND ((status)::text = 'TODO'::text))
  Heap Blocks: exact=1639
  Buffers: shared hit=1647
  ->  Bitmap Index Scan on idx_tasks_project_status  (cost=0.00..28.73 rows=2031 width=0) (actual time=0.492..0.492 rows=1999 loops=1)
        Index Cond: ((project_id = 1) AND ((status)::text = 'TODO'::text))
        Buffers: shared hit=8
Planning Time: 2.045 ms
Execution Time: 3.993 ms
```

Ya no hay `Filter`/`Rows Removed by Filter`: el `status` entra directo en el
`Index Cond`, el index scan devuelve exactamente las 1999 filas que hacen falta (no
5965 para despues descartar 3966), el costo estimado baja de `82.86..5274.79` a
`29.24..3809.61`, y los buffers leidos bajan a menos de la mitad (1647 contra 3448).

### MySQL

Mismo query, `EXPLAIN ANALYZE` (formato arbol de MySQL 8).

**Antes** (solo `idx_tasks_project_id`, indice compuesto dropeado a mano para medir
este estado):

```
-> Filter: (tasks.`status` = 'TODO')  (cost=1616 rows=622) (actual time=0.0597..19.5 rows=2070 loops=1)
    -> Index lookup on tasks using idx_tasks_project_id (project_id=1)  (cost=1616 rows=6217) (actual time=0.0507..18.5 rows=6217 loops=1)
```

El index lookup trae las 6217 filas del proyecto; el `Filter` exterior las recorre una
por una para quedarse con las 2070 que son `TODO`.

**Despues** (con `idx_tasks_project_status` recreado):

```
-> Index lookup on tasks using idx_tasks_project_status (project_id=1, status='TODO')  (cost=724 rows=2070) (actual time=0.0737..4.12 rows=2070 loops=1)
```

Un solo paso: el index lookup ya filtra por las dos columnas (`project_id=1,
status='TODO'`) y devuelve directamente las 2070 filas que hacen falta, sin `Filter`
posterior. El costo estimado baja de 1616 a 724 y el tiempo real de ejecucion de
~19.5ms a ~4.12ms (unas 4-5x), con una fraccion de las filas tocadas (6217 -> 2070).

## CI/CD

GitHub Actions corre en cada push/PR a `main` (`.github/workflows/ci.yml`):

- **`test-postgres-mysql`**: corre `PostgresCrudIT` y `MySqlCrudIT` (el mismo flujo de
  `AbstractCrudIT` descrito en la seccion de Tests) con `mvn verify
  -Dit.test=PostgresCrudIT,MySqlCrudIT`. Estas 2 clases ya administran su propio
  contenedor real via Testcontainers, y los runners de GitHub Actions para Ubuntu
  traen Docker funcionando de fabrica, asi que Testcontainers corre ahi sin el
  problema de Docker Desktop para Windows documentado mas arriba (que es especifico
  de esta maquina de desarrollo, no del codigo). Por eso el workflow **no** usa el
  bloque `services:` de Actions para Postgres/MySQL: hubiera sido un contenedor de
  mas, sin usar, en paralelo al que el propio test ya levanta y destruye solo.
- **SQL Server y Oracle quedan fuera del CI automatico**, a proposito: las imagenes
  son mucho mas pesadas (SQL Server ronda el GB, `oracle-free` varios GB mas un
  arranque de varios minutos inicializando datafiles) y harian el pipeline lento y
  caro para un repo de portafolio. El codigo de esos 2 motores (incluidos los stored
  procedures nuevos) esta igual de verificado, pero a mano con `docker compose` +
  `curl`/`sqlcmd` contra contenedores reales (ver "Que se probo realmente" y la
  seccion de los stored procedures mas arriba), no en este pipeline.
- **`codeql`**: analisis estatico de Java con CodeQL (`github/codeql-action`),
  tambien en cada push/PR a `main`.
